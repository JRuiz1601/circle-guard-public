Diseno elegido

- Se agrego el job `OWASP ZAP Gateway Scan` a `.github/workflows/quality.yml`.
- El job usa un entorno efimero de GitHub Actions:
  - Redis 7.2 como service container.
  - gateway iniciado desde `:services:circleguard-gateway-service:bootJar`.
  - `SERVER_PORT=8080`.
  - `SPRING_DATA_REDIS_HOST=127.0.0.1`.
- El target ZAP es `http://127.0.0.1:8080`.
- Se usa `zaproxy/action-full-scan@v0.13.0`.
- La action oficial ejecuta ZAP con Docker y red host, por lo que el target local del runner es accesible desde el contenedor.

Justificacion de no usar docker-compose.dev.yml

- `docker-compose.dev.yml` solo contiene PostgreSQL, Neo4j, Kafka, Redis y OpenLDAP.
- No expone gateway.
- Para este punto, el gateway solo necesita Redis para que sus endpoints y healthcheck arranquen de forma reproducible.
- Levantar todo el stack o cambiar compose agregaria superficie innecesaria y podria invadir trabajo de infraestructura no requerido para Tomas.

Justificacion de no usar Kind en este bloque

- PlanSprint2.md permite gateway expuesto por un entorno efimero o por docker compose/Kind si existe soporte suficiente.
- El entorno efimero de GHA con bootJar + Redis es suficiente para DAST del gateway y evita depender de imagenes locales, registros o configuracion Kubernetes de otros tracks.
- No se modifica Terraform, RBAC, TLS, Secrets ni aprobaciones.

Politica de fallos y hallazgos

- `fail_action: true`.
- No se usa `continue-on-error`.
- No se agrego archivo de reglas para ignorar alertas.
- Por tanto, los hallazgos no quedan ocultos por configuracion de este job.
- Si ZAP detecta alertas que produzcan exit code de fallo, el job debe fallar y el reporte queda como artifact para revision.

Artifacts esperados

- `zap-gateway-report`: artifact generado por `zaproxy/action-full-scan`.
- `zap-gateway-runtime-log`: log de arranque del gateway para diagnostico del entorno efimero.

5. El workflow publica `zap-gateway-report`.
